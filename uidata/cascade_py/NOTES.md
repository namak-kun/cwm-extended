# Cascade Python UI-transition dataset notes

- App: `cascade_app.py`, a Streamlit onboarding/wizard form with 10 text fields, 6 number fields, 3 booleans, and a dynamic department list. The app stores model state in `st.session_state.model` and all widget callbacks call the shared `cascade_logic.dispatch` update path.
- Cascading rules: email/password/confirm coupling; plan/country/region/VAT/state conditional requirements; date duration constraints; plan-dependent seat bounds; enterprise security and department-approval gates; coupon eligibility; budget totals from base/seat/security/department costs; step completion, blocked steps, error summary, warnings, and `can_submit` recomputation.
- Depth emphasis: a single action recomputes required/visible fields, allowed regions, nested department errors, price totals, budget margin, five-step wizard completion, blocked steps, error summary, and final submit gate.
- Oracle method: `build_cascade_dataset.py` drives the real Streamlit app headlessly with `streamlit.testing.v1.AppTest`; `truth_state` is the canonicalized `session_state.filtered_state["model"]` after each widget action.
- Prompt method: each row embeds self-contained Python (`dispatch(state, action)->state` plus `main()  # << START_OF_TRACE`) copied from `cascade_logic.py`; no Streamlit import is required inside `prompt_src`.
- Verification: final build kept 112 transitions and dropped 0.
